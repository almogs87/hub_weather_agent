# Architecture and design

Browser -> same-origin HTTP API -> validated Service -> approved model planner/tool -> deterministic weather or scenario engine -> evidence-backed result -> browser.

The application uses Python, Pydantic and SQLite. The HTTP server uses Python's standard library instead of the originally proposed FastAPI stack, reducing installation requirements for the local interview demo. Production serving/deployment is a separate extension. The server binds to loopback and exposes explicit routes only.

Live planning defaults to Groq chat completions with a strict JSON response schema derived from Intent. The retained OpenAI adapter uses the Responses API with a strict function schema. Every field is required (nullable where appropriate), unknown fields are rejected, and Python validates arguments again before execution. The model receives registered coordinates/IDs and prior intent; it cannot execute code or make up tool implementations. At most one plan is executed per message. OpenAI errors/refusals do not switch to the demo parser. LLM_PROVIDER and LLM_MODEL select the adapter/model; GROQ_API_KEY or OPENAI_API_KEY supplies its credential. No key enters the browser or database.

Weather and network calculations are deterministic Python. Narratives are assembled from those results rather than generated by a second LLM; this keeps displayed numbers consistent with evidence. The provider adapter can be replaced without changing analytics. DemoPlanner is explicitly opt-in, limited and not AI.

SQLite stores registered locations and per-conversation context, including the most recent resolved intent, explanation and optional explicitly supplied network. It uses short-lived connections closed after each transaction. This first version does not retain a full user message transcript. Weather responses are request-keyed file caches with timestamps and integrity hashes. The exported development session is included in the repository root.

The allocator runs a minimum-cost maximum-flow algorithm over eligible hub-demand links. It maximizes served divisible daily demand before minimizing distance. It respects capacities and service components, reroutes through residual paths, and breaks equal-cost choices in stable ID order. Weather replay maps actual daily snowfall to explicitly assumed capacity fractions/recovery; weather evidence and profile assumptions accompany the output.

Repository structure and commands are in README.md. Runtime databases, caches and credentials are excluded from version control. Verification includes numerical regression tests, strict-schema/provider mocks, conversation evaluation cases and headless browser checks. An earlier seven-case live Groq evaluation passed; the expanded live-model and current-interface end-to-end checks remain open.

Official structured function guidance: https://developers.openai.com/api/docs/guides/structured-outputs

Provider modules are in app/providers.py; the shared prompt and Intent contract are independent of transport. See model-providers.md for the accepted switching and evaluation plan.
