# Model providers and switching plan

## Supported now

- Groq (default), starting model openai/gpt-oss-20b.
- Other Groq models that support strict JSON-schema responses; openai/gpt-oss-120b is a documented next candidate.
- OpenAI Responses API adapter retained; select a model with strict function-call support and your own API access.
- Demo parser remains explicitly opt-in with --demo.

Selection is configuration, not a change to weather/network code. LLM_PROVIDER selects groq or openai. LLM_MODEL overrides the model. GROQ_MODEL and OPENAI_MODEL remain provider-specific alternatives. The UI identifies the selected provider/model. Unknown providers fail explicitly. No automatic paid-provider or demo fallback occurs on quota, refusal or invalid output.

## Secure Groq startup

1. Create a key at https://console.groq.com/keys . Do not paste it into chat or commit it.
2. Stop the demo server (Ctrl+C).
3. From the project directory run:

~~~powershell
.\scripts\start-live.ps1
~~~

The launcher prompts for the key with hidden input, supplies it to the child process, and restores previous process environment settings on exit. It does not save a key file. Open http://127.0.0.1:8000 and confirm LIVE AI / groq / openai/gpt-oss-20b. Start a new conversation for a clean evaluation.

If you already manage environment variables securely, set GROQ_API_KEY, LLM_PROVIDER=groq and LLM_MODEL=openai/gpt-oss-20b, then run python -m app.server without --demo.

## Evaluate and switch

Stop the server before using the launcher to evaluate:

~~~powershell
.\scripts\start-live.ps1 -Action evaluate
.\scripts\start-live.ps1 -Model 'openai/gpt-oss-120b' -Action evaluate
.\scripts\start-live.ps1 -Model 'openai/gpt-oss-120b'
~~~

Evaluation reuses the same six conversation cases and synthetic weather across models, records provider/model, pass/fail, planned intents and latency, and writes ignored eval-results/*.json files. Compare these reports rather than changing prompts and model simultaneously. Rate limits may cause failures; quota failure is not evidence of poor planning quality. Free plans are not unlimited.

For OpenAI, use -Provider openai -Model YOUR_AVAILABLE_MODEL (prompts for OPENAI_API_KEY). Gemini/Ollama/custom endpoints are planned adapters, not currently supported by a configuration-only change.

## Contract and scope

Both adapters return the same Pydantic Intent object. Groq uses strict response_format JSON schema because its structured-output feature does not combine with tool use. Application code validates that plan and dispatches approved tools. OpenAI uses a strict plan_analysis function call. All numerical results are generated by the same deterministic engine. Provider failures never execute an unvalidated plan.

Current checks: mocked adapter success, malformed/truncated output, missing keys, quota errors, provider selection and model switching. Live Groq accuracy and account/model access remain unverified until a real key is configured locally and the live evaluation passes.

- [x] Hidden-key local launcher; no secrets in reports.
- [x] Repeatable model-specific evaluation reports.
- [ ] Verify starter Groq model live and fix any actual schema compatibility issues.
- [ ] Run six live conversation cases and a browser follow-up sequence.
- [ ] Repeat with the second model and record quality/latency/quota tradeoffs.
- [ ] Add another provider only when needed, with adapter tests and the same live acceptance gates.
